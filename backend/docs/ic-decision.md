# Фіксація рішення ІК

T6714. Джерела: 12 критеріїв картки задачі, прочитані 05.10.2026 в авторизованій сесії; Wiki проєкту: FR-07, FR-95, Application Structure / картка об'єкта.

## API

`PATCH /api/objects/{id}/ic-decision`. Існуюча авторизація JWT cookie та CSRF `X-XSRF-TOKEN`. Відповідь має `Cache-Control: no-store`. [OpenAPI](ic-decision.openapi.json).

Дозволені поля: `decision`, `date`, `conditions`, `refusalComment`, `version`, `confirmationToken`, `assignees`. Невідомі поля й невідповідні типи повертають 422 із назвою поля. Дата — YYYY-MM-DD; `version` — поточна версія об'єкта з його відповіді, обов'язкове ціле невід'ємне число.

| Рішення | Умови | Наступний статус |
|---|---|---|
| APPROVED | Не передаються | COMMERCIAL_TERMS_APPROVAL |
| APPROVED_WITH_CONDITIONS | Обов'язковий непорожній текст, до 50 символів | COMMERCIAL_TERMS_APPROVAL |
| REFUSED | Не передаються; обов'язковий коментар відмови до 50 символів | REFUSED; причина IC_NOT_APPROVED |

Дата ІК обов'язкова завжди. Пробіли по краях умов прибираються. Рішення доступне тільки в IC_PREPARATION. Ролі перевіряються за поточними даними БД: REGIONAL_MANAGER у своєму регіоні та його вкладених регіонах або DEVELOPMENT_DIRECTOR у всій мережі. CEO, SUPERADMIN, MANAGER, CONTRACT_MANAGER та вимкнені користувачі не мають цього права.

## Прев'ю й підтвердження

1. Клієнт передає рішення, дату, умови та версію без `confirmationToken`.
2. За наявності активного шаблону для пари «цільовий статус + тип договору», якщо у цільового статусу немає ACTIVE-набору об'єкта, повертається 200 із `saved=false`, поточним статусом, списком `tasks` та `confirmationToken`. Рішення, історія, статус і задачі не змінюються.
3. Клієнт показує задачі з виконавцями та строками. Скасування модалки не потребує запису в API.
4. Після явного підтвердження клієнт повторює ті самі дані з отриманим токеном. Відповідь `saved=true` містить новий статус і версію.

Токен — відбиток прев'ю, а не credential. Він прив'язаний до користувача, об'єкта, версії, рішення, дати, умов, правила переходу, складу шаблону, строків, виконавців і незавершених задач. Інші дані або зміна прев'ю повертають 409 без запису; треба отримати й підтвердити нове прев'ю.

Якщо шаблону немає або він порожній, сценарій ІК зберігає рішення одразу без задач, як передбачають FR-95 і T5806. Факт відсутності шаблону записується в історію, аудит і подію адміністратору. Для відмови комерційні задачі не створюються. Якщо виконавець не визначився, прев’ю повертає saved=false, confirmationToken=null та список кандидатів. Вибір передається картою assignees: UUID елемента → UUID користувача. Повторний запит із вибором видає токен; підтвердження з невирішеним призначенням повертає 422. [Правила призначення](task-assignment.md). Кілька активних шаблонів для однієї пари дають `409 TASK_TEMPLATE_CONFIGURATION_ERROR` без збереження рішення або переходу. [Правила підбору](task-template-selection.md).

## Транзакція й історія

Об'єкт блокується на час сценарію. Застаріла версія повертає 409. Конкурентне підтвердження не створює другий набір: після першого збереження об'єкт уже не в IC_PREPARATION.

Системне правило вибирається з таблиці переходів за початковим статусом і рішенням. За актуальними деталями T6712 від 12.10.2026 IC_APPROVED та IC_APPROVED_WITH_CONDITIONS використовують NONE, IC_REFUSED — CANCEL_ALL. Відмова скасовує всі незавершені задачі об'єкта та повідомляє виконавців; DONE і CANCELLED зберігаються. Позитивне рішення не змінює існуючі задачі. Нові комерційні задачі створюються після підтвердження прев'ю лише за відсутності активного набору цільового статусу. Наявний ACTIVE-набір виключає нарізку, прев'ю й повідомлення про відсутній шаблон.

У `object_history` створюються рівно два записи: IC_DECISION з користувачем-автором, датою та умовами; STATUS із SYSTEM і порожнім author_id. При відмові зберігаються статус до відмови й системна причина. Скасування задач має окрему історію. Помилка на будь-якому кроці відкочує рішення, статус, історію, скасування та створення задач.

## Межа інтеграції Tasks

На момент роботи модуль Tasks у develop містив тільки пакети. Для цього сценарію додані public API `ObjectTaskTransition`, таблиці task_templates, task_template_items, tasks, task_history та транзакційний адаптер. Objects не імпортує внутрішні типи Tasks.

Шаблон містить статус-тригер і тип договору; позиція — назву, явно налаштованого виконавця та зміщення дедлайну в календарних днях від дати ІК. Прев'ю показує результат цього правила. Це конкретне правило даного адаптера, а не затверджена матриця Workflow: матриця й розширений розрахунок строків залишаються в Epic Tasks. Шаблони й реальні призначення не вигадані й не сідуються. Поточний адаптер не реалізує адмінку шаблонів, залежності задач, сповіщення або їх ручне редагування.

Склад шаблону зчитується під блокуванням; створені задачі отримують копії назви, виконавця й дедлайну, тому наступне редагування шаблону не змінює їх. Майбутні сценарії запису задач мають блокувати батьківський об'єкт у тому самому порядку.

## Міграція й залежність

Новий changeset 20261005-tasks-ic-transition має явний rollback. Опубліковані міграції не змінюються. Правила T6712 із T5770 / MR !39 вже включені в develop. Гілка оновлена з develop зі збереженням опублікованого порядку changelog. Нова міграція не додає бізнес-сідів.

## Перевірки

Інтеграційні тести використовують справжні PostgreSQL і Redis: три рішення, права й регіони, валідація, прев'ю, підтвердження, зміна прев'ю, повторні й конкурентні запити, CSRF, збереження задач, атомарний відкат і rollback/reapply міграції.

## Уточнення T5770 від 05.10.2026

Назви результатів: APPROVED — «Затверджено», APPROVED_WITH_CONDITIONS — «Затверджено з умовою», REFUSED — «Відмова». Коди API збережені. `refusalComment` — обов'язковий непорожній текст до 50 символів для REFUSED; повертається у відповіді та записується в подію IC_DECISION. Відсутнє поле, null, порожній текст, лише пробіли або понад 50 символів повертають 422 із полем refusalComment. Межа рахується в Unicode-символах після видалення крайніх пробілів; нерозривні пробіли нормалізуються. Для інших рішень поле не передається або дорівнює null. Історичні рішення без коментаря збережені.

Для позитивного рішення спочатку перевіряється ACTIVE-набір цільового статусу. Якщо його немає, вибирається активний шаблон цільового статусу й типу договору без фіксованого прапорця статусу. Неактивний або відсутній шаблон не створює задач і не вимагає підтвердження. Знайдений активний шаблон вимагає прев'ю й підтвердження; зміна умов, коментаря або шаблону змінює токен.

Тип договору береться з довідника Основний / Попередній, код передається через публічний API Tasks. Для історичного об'єкта вибір шаблону за новим кодом має пріоритет; за його відсутності підтримується шаблон із колишнім текстовим типом договору. UUID і налаштування старих шаблонів не змінюються. Поля POST створення описані в [object-creation.md](object-creation.md).

Окремий changeset `20261005-ic-transition-task-policy` змінює дію лише трьох системних правил ІК на NONE. Rollback повертає попередній CANCEL, версії й час зміни конфігурації оновлюються. Об'єкти, задачі, шаблони та історія не змінюються. Опубліковані changeset залишаються без правок.
