# Почта для локальной разработки

## Тестовый SMTP

Из `backend/` скопируйте `.env.example` в `.env`. Заполните
`SEED_TEST_USER_EMAIL` и `SEED_TEST_USER_PASSWORD`, затем выполните:

```bash
docker compose up --build
```

Пароль задаётся разработчиком: минимум 12 символов, максимум 72 байта UTF-8.
Значения паролей, почтовых доступов и реальных адресов в репозиторий не добавляются.

В образце уже выбран Mailpit. Backend отправляет ему письма по SMTP на
`mailpit:1025`. Письма доступны на `http://localhost:8025`; порт меняется через
`MAILPIT_HOST_PORT`. Интерфейс привязан к loopback, SMTP-порт на хост не открыт.
Mailpit работает без внешнего почтового аккаунта и не пересылает письма в Gmail
или другие внешние ящики. Даже письмо на реальный адрес останется в Mailpit.
Письма хранятся в контейнере и удаляются при его пересоздании.

Это позволяет всей команде проверить вход без общих SMTP-паролей. Возможности
сервера описаны в [документации Mailpit](https://mailpit.axllent.org/docs/install/docker/).

## Тестовый пользователь

После миграций backend автоматически создаёт активного менеджера в регионе
`DEMO_MAIL`. Пароль хранится как BCrypt-хеш. Telegram не привязан, доверенного
устройства нет, поэтому первый вход требует код из письма.

Seed включён только при активном `dev` и выключен при `stage`, `prod`, а также
их сочетании с `dev`. В compose стенда параметры тестового пользователя не
передаются. Пустой email пропускает seed; некорректные email или пароль также
пропускаются с сообщением в журнале и не мешают запуску.

Повторный запуск не меняет пароль, роль, статус, Telegram или устройства
существующего пользователя. Регистр email не влияет на проверку дубликатов.
Изменение пароля в `.env` не сбрасывает пароль уже созданного аккаунта.
Для нового тестового аккаунта укажите другой email; для существующего используйте
обычное восстановление пароля.

## Проверка входа

1. Откройте `http://localhost:3000` в новом профиле браузера и войдите с email
   и паролем из `SEED_TEST_USER_*`.
2. Откройте Mailpit, найдите письмо получателю и введите шестизначный код.
3. Убедитесь, что вход завершился. Код действует пять минут и используется один раз.
4. Повторный вход в том же браузере проходит с доверенного устройства; новый
   профиль браузера снова запросит код.

Синтетические пользователи ручного сида с адресами `example.com` также получают
письма в Mailpit. Для внешней доставки нужен адрес настоящего ящика.

## Доставка на настоящую почту

Нужен отдельный SMTP-аккаунт проекта с разрешённым адресом отправителя. Его
доступы сохраняются только в локальном `.env` и передаются команде через
согласованный менеджер секретов. Настройки Mailpit заменяются следующими:

| Переменная | Значение от почтового провайдера |
| --- | --- |
| `SMTP_HOST` | SMTP-сервер |
| `SMTP_PORT` | Обычно 587 для STARTTLS или 465 для TLS |
| `SMTP_USERNAME` | Логин |
| `SMTP_PASSWORD` | SMTP-токен или пароль приложения |
| `SMTP_AUTH` | `true` |
| `SMTP_STARTTLS_ENABLED` | `true` для STARTTLS; `false` для порта с TLS |
| `SMTP_SSL_ENABLED` | `false` для STARTTLS; `true` для порта с TLS |
| `AUTH_EMAIL_FROM` | Разрешённый отправитель |
| `SEED_TEST_USER_EMAIL` | Реальный ящик получателя |
| `SEED_TEST_USER_PASSWORD` | Пароль тестового пользователя CRM |

STARTTLS при включении обязателен. Проверка сертификата и имени SMTP-сервера
включена. Отключать TLS для внешнего SMTP не следует. Отправители приглашений
и восстановления по умолчанию используют `AUTH_EMAIL_FROM`; при необходимости
их можно переопределить через `USER_INVITATION_MAIL_FROM` и `PASSWORD_RESET_MAIL_FROM`.

После изменения `.env` выполните `docker compose up -d --force-recreate app`.
Повторите проверку входа, беря код уже из реального ящика, включая папку спама.
При смене адреса seed создаст отдельного пользователя без удаления старого.

Перед передачей аккаунта команде проверьте в кабинете провайдера:

- дневной и минутный лимиты отправки, ограничения на получателей;
- разрешённый отправитель и требуемую проверку домена;
- ограничения тестового тарифа и срок действия SMTP-токена;
- получение кода каждым тестовым получателем и успешное завершение входа.

Конкретные лимиты зависят от аккаунта и тарифа. Пока внешний аккаунт не подключён,
доставка на реальную почту и его лимиты не проверены.

## Ошибки доставки

Пустые обязательные настройки дают `503 Email confirmation is unavailable`.
В журнале перечисляются имена отсутствующих переменных: `SMTP_HOST`,
`SMTP_USERNAME`, `SMTP_PASSWORD`, `AUTH_EMAIL_FROM`. Логин и пароль обязательны
при `SMTP_AUTH=true`; локальный Mailpit их не требует.

Ошибка подключения, аутентификации или отправки также даёт `503`. Созданный
challenge переводится в `REJECTED`: код не позволяет завершить вход. Журнал
содержит категорию ошибки, без паролей, кодов и содержимого писем. После
исправления настроек начните вход заново; обычные ограничения частоты сохраняются.

## Автоматические проверки

`SmtpLoginIT` использует PostgreSQL, Redis и Mailpit в Testcontainers. Проверяются
получение письма по SMTP, вход по извлечённому коду, запрет повторного применения,
отказ при неверном SMTP-пароле и недоступном сервере, повторный seed без изменения
аккаунта и пропуск пустых настроек. Unit-тесты проверяют исключение seed из других
профилей и безопасные сообщения об ошибках SMTP.

```bash
mvn -Pintegration -Dit.test=SmtpLoginIT,UserManagementIT,PasswordRecoveryIT,AuthLoginIT verify
```

Эти проверки подтверждают локальный почтовый путь. Доставку во внешний ящик
нужно проверить отдельно с рабочим SMTP-аккаунтом.
