# Поля объекта и справочники T5770

Актуализация 05.10.2026 по восьми непомеченным критериям задачи 05770. Wiki проекта проверена: Product Requirements Documents и Application Structure пока содержат прежний перечень полей; текущие названия и состав взяты из присланной карточки задачи. Правила переходов T6712 сохраняются.

## Объект

Объект сохраняет имя, тип, адрес, регион, менеджера, статус, статусы до паузы и отказа, WGS84, площади, автора, время создания и версию. `getGoogleMapsUrl()` вычисляет ссылку из текущей точки входа: широта, затем долгота, разделитель кодируется как `%2C`. Ссылка не хранится в БД и не требует запроса к Google. Формат соответствует [Google Maps URLs](https://developers.google.com/maps/documentation/urls/get-started).

`ObjectSpecifications` объединяет технический и коммерческий блоки и ссылку `contract_type_id`. `ObjectMilestones` хранит даты. Все новые поля необязательны до заполнения соответствующего этапа; требования создания и переходов продолжают проверяться своими сценариями.

| first_floor_area | Первый этаж, м² |
| second_floor_area | Второй этаж, м² |

Числовые значения — `numeric(14,2)`, неотрицательные. Домен отвергает превышение точности и дробных разрядов, чтобы не сохранять неявно округлённое значение. Enum проверяется и в PostgreSQL.

## ІК и даты

Результаты ІК: APPROVED — Затверджено; APPROVED_WITH_CONDITIONS — Затверджено з умовою; REFUSED — Відмова. Дата обязательна при любом решении. Условия и комментарий отказа ограничены 50 Unicode-символами. Условия обязательны для условного утверждения; комментарий отказа обязателен и принимается только при отказе. HTTP-коды результатов сохранены. [Контракт решения ІК](ic-decision.md).

| Поле | Назначение |
|---|---|
| contract_signed_date | Дата подписания основного договора |
| preliminary_contract_signed_date | Необязательная дата подписания предварительного договора |
| commissioning_date | Дата ввода в эксплуатацию |
| construction_acceptance_planned_date / construction_acceptance_actual_date | Акт принятия на БМР: план / факт |
| opening_planned_date / opening_date | Открытие: план / факт |
| payment_act_planned_date / payment_act_actual_date | Акт для оплат: план / факт |

Существующая колонка opening_date остаётся фактической датой. План и факт могут отличаться; дополнительное ограничение порядка плановых дат не вводится. Сохраняется правило: фактическое открытие не раньше подписания договора.

План открытия вычисляется из планового акта на БМР и срока БМР в календарных днях; ручное редактирование плана недоступно. `short_comment` хранит необязательный комментарий до 200 символов. [Даты, расчёт и условия подписания](object-lifecycle.md).

## Справочники и триггеры

`contract_types`: PRIMARY — Основний, PRELIMINARY — Попередній. UUID, уникальный код, название, активность, технические даты и версия. `objects.contract_type_id` — внешний ключ с ON DELETE RESTRICT и индексом. Удалить используемый тип договора нельзя.

Активные типы объекта: LAND_PLOT — Земельна ділянка, BUILT_IN_PREMISES — Вбудоване приміщення, SHOPPING_CENTER — ТЦ, HANGAR — Ангар. RESIDENTIAL_GROUND_FLOOR сохранён с прежним UUID как неактивный; существующие объекты не перепривязываются к другому типу автоматически.

В object_statuses нет сохранённого флага триггера. `StatusTaskTriggerQuery.isTrigger(statusId)` проверяет наличие активного task_templates для статуса; активация и отключение шаблона отражаются без изменения сидов и перезапуска. При нарезке используется активный шаблон соответствующего типа договора. Для старого объекта после привязки к справочнику сохраняется выбор шаблона по прежнему текстовому типу; если настроен шаблон по новому коду, он имеет приоритет. Шаблоны и их UUID не переписываются. Изменение состава задач не меняет ранее созданные задачи.

Использована реализация Tasks из T6714 / MR !43. Реальные матрицы задач не сидируются; их содержание утверждает клиент. Эта доработка не добавляет интерфейс администратора шаблонов.

## Обновление и откат

Новая миграция `20261005_objects_field_revision` выполняется поверх опубликованных изменений; прежние SQL и checksums не переписаны. Старые commercial_terms, technical_specifications и свободный contract_type сохранены. Тип договора сопоставляется только по точному коду или названию нового справочника; неизвестный текст не угадывается.

Старые условия ІК перенесены в legacy_investment_committee_conditions без обрезки. Значения до 50 символов копируются в новое varchar(50); более длинные доступны через доменный getter из исторической колонки. Новое решение пишет короткое поле и очищает старое значение в одной транзакции. Новое решение записывается в историю существующего сценария.

Таблицы object_status_trigger_backups и object_type_revision_backups содержат исходную конфигурацию для точного отката. Повторное update Liquibase сохраняет UUID и число строк. Rollback возвращает прежние колонки, справочники и старые условия. Если новый Ангар уже используется, удаление сидового типа при откате блокируется внешним ключом. Рабочий downgrade после заполнения новых полей требует резервирования этих данных: старая версия модели не может их хранить.
