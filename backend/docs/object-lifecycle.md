# Даты объекта и условия подписания

Дополнение к модели T5770 по актуальным критериям задачи в KeySpace.

## Даты и комментарий

`contractSignedDate` остаётся датой подписания основного договора. Добавлены `preliminaryContractSignedDate` — дата подписания предварительного договора, и `commissioningDate` — дата ввода в эксплуатацию. Обе даты доступны через PATCH карточки и возвращаются в `workflow.milestones`. Договорной отдел видит их в своей технической карточке. Дата предварительного договора не обязательна для подписания основного.

`shortComment` — необязательный короткий комментарий до 200 символов. Поддерживается при создании, редактировании, импорте и экспорте. Пробелы по краям удаляются, пустой текст сохраняется как null. Изменения дат и комментария попадают в историю. Ограниченный пин чужого объекта не содержит комментарий.

## План открытия

`openingPlannedDate = constructionAcceptancePlannedDate + commercialTerms.constructionTermDays`.

Срок БМР задаётся в календарных днях, включая выходные. Ноль означает день планового акта. При отсутствии любого из двух значений результат равен null. Пересчёт выполняется при изменении даты акта или коммерческого блока; статус объекта при этом не меняется. Фактическое открытие по-прежнему оформляется отдельным переходом.

Поле плана открытия доступно только для чтения в карточке. Для изменения плана нужно менять исходную дату или срок БМР. Домен пересчитывает результат до сохранения, а триггер PostgreSQL обеспечивает ту же формулу для записей через другие пути. В шаблоне импорта v2 колонки `openingPlannedDate` нет. В уже принятых строках прежнего формата указанное значение проверяется на совпадение с расчётом, иначе строка отклоняется с указанием поля. Состав шаблона описан в [импорте объектов](object-import.md).

## Переход SIGN_CONTRACT

В таблице обязательных полей настроены:

- `CONTRACT_SIGNED_DATE` — дата основного договора;
- `CONTRACT_TYPE` — активный тип договора;
- `COMMISSIONING_DATE` — ввод в эксплуатацию;
- `CONSTRUCTION_ACCEPTANCE_PLANNED_DATE` — плановый акт на БМР;
- `CONSTRUCTION_TERM_DAYS` — срок БМР, допускается 0;
- `OPENING_PLANNED_DATE` — вычисленный план открытия.

Настройки обязательных завершённых задач хранятся отдельно в `object_transition_required_tasks`. Сид SIGN_CONTRACT содержит:

| Код элемента шаблона | Задача |
|---|---|
| APPROVE_LOTUS_CONTRACT | Погодити договір в системі Lotus |
| APPROVE_FINANCIAL_MODEL | Погодити фінансову модель |
| APPROVE_QUESTIONNAIRE | Погодити опитувальний лист |

Проверка выполняется по кодам элементов, сохранённым в неизменяемой версии шаблона. Для каждого обязательного элемента выбирается последний набор этого элемента на исходном этапе объекта, включая отменённые наборы. Более новый набор без этого элемента не влияет на результат. Только DONE считается завершением: отменённая задача и отсутствие задачи в последнем наборе оставляют условие невыполненным. Прежние задачи с привязкой к элементу шаблона поддерживаются как резерв, если для соответствующего кода нет набора. Название задачи и ручная задача с таким же названием не заменяют элемент шаблона.

Остальные незавершённые задачи обрабатываются действующим `unfinished_task_action`. Обязательные задачи повторно проверяются при подтверждении и обработке очереди. Состав требований включён в отпечаток превью. Ручной переход при невыполненных условиях возвращает 422 с кодом `TRANSITION_CONDITIONS_NOT_MET`, всеми отсутствующими полями и обязательными задачами; записей не меняет. `unmetConditions.incompleteTasks` содержит id, код, название и статус существующих задач, `missingTaskCodes` — коды отсутствующих задач.

При вводе допустимой даты основного договора или фактического открытия в карточке условия проверяются тем же сценарием. Если обязательные поля или задачи ещё не готовы, дата сохраняется без смены статуса, а ответ 200 содержит `unmetConditions` и актуальную версию. То же правило действует для `/milestones`. Ошибки формата, прав, хронологии и версии по-прежнему отклоняют запись. После выполнения условий можно повторно отправить сохранённую дату с новой версией; при наличии шаблона потребуется превью и подтверждение. Если условия изменились после превью, подтверждение возвращает 409 без сохранения.

Статусный и milestone API принимают дополнительные поля `commissioningDate`, `preliminaryContractSignedDate`, `constructionAcceptancePlannedDate`, `constructionTermDays` вместе с датой подписания. Общий PATCH карточки проверяет подготовленные значения всего запроса, поэтому дату акта, срок БМР и дату договора можно сохранить одним подтверждённым действием. Права перехода и ограничения изменения типа договора сохраняются.

Миграция сопоставляет существующие элементы с известными названиями трём кодам. Остальные получают уникальный служебный код; код фиксируется при создании новой версии шаблона. В шаблоне договорного этапа эти три элемента должны иметь указанные коды. Миграция не создаёт шаблон с неподтверждёнными исполнителями или сроками.

## Обновление и откат

Миграция `20261022_object_lifecycle` дополняет опубликованную схему. Старые UUID и задачи сохраняются. Плановые даты пересчитываются по новой формуле; прежние значения и версии объектов сохранены в `object_opening_plan_backup`. Изменение рассчитанного значения повышает версию объекта. Версия политики подписания также повышается, поэтому перед подтверждением потребуется актуальное превью.

Откат восстанавливает схему и прежние значения у объектов, не изменённых после миграции. Если заполнены новые даты или комментарий, изменена политика подписания либо настроены дополнительные коды задач, откат останавливается с понятной ошибкой. Перед откатом таких данных требуется отдельно сохранить и согласовать их перенос. Повторный запуск Liquibase не дублирует требования и коды.
