# Відмова по об'єкту

T6713: шість Acceptance Criteria та чотири Edge cases у картці задачі. Використовується сценарій зміни статусу T6712, без окремого механізму переходів.

## Запит

`GET /api/objects/{id}/refusal-reasons` повертає активні ручні причини у форматі `{id, code, name}`, відсортовані за назвою й кодом. Системні та неактивні значення виключені. Доступ перевіряється за користувачем, власником і регіоном об'єкта. Відповідь має `Cache-Control: no-store`.

Відмова виконується через `POST /api/objects/{id}/status`:

```json
{
  "status": "REFUSED",
  "version": 3,
  "refusalReasonId": "UUID з довідника"
}
```

Потрібні чинна сесія та CSRF. Якщо для цільового статусу налаштований активний шаблон, застосовуються прев'ю й підтвердження T6712. До `saved=true` об'єкт, задачі й активне погодження не змінюються.

Відсутня, невідома чи неактивна причина повертає 422 з `violations[].field=refusalReasonId`. «Не погоджено на ІК» — системна причина, ручний вибір також повертає 422. Попередня збережена причина не замінює обов'язковий вибір при новій відмові.

## Доступ

Дозволені ролі й умови беруться з `object_status_transitions` та пов'язаних таблиць T6712. До ІК відмову можуть поставити менеджер свого об'єкта, провідний регіону і директор з розвитку. Починаючи з IC_PREPARATION — провідний та директор. Для паузи враховується етап до паузи.

`object_transition_validation_roles` визначає тільки спосіб повідомлення про недоступний перехід: 422 для налаштованої ролі замість загального 403. Запис у цій таблиці не надає права переходу або редагування полів. Сід містить MANAGER для пізніх ручних відмов. Код не порівнює назви етапів для цього обмеження.

CONTRACT_MANAGER отримує 403 при ручній відмові з будь-якого статусу, включно з REFUSED. Якщо прямого переходу немає, перевіряються ролі активних переходів до цільового статусу, після чого допустима роль отримує 422 за відсутність маршруту.

Це правило відповідає актуальному T6713 і таблиці T6712. У PRD FR-11 від 01.10 контрактній ролі ще дозволена пізня відмова; при реалізації застосовано новіші критерії задачі. Системна відмова ІК також використовує CANCEL_ALL за актуальною таблицею та правками T6712 від 12.10.2026.

## Тег причини та аналітика

Тег є типізованим посиланням `objects.refusal_reason_id` на довідник `refusal_reasons`. UUID і стабільний код ідентифікують причину, назва використовується для відображення. Друга копія тегу чи довільний текст не зберігаються. Чинний FK з ON DELETE RESTRICT та індекс `ix_objects_refusal_reason` забезпечують цілісність і пошук.

`GET /api/objects/{id}/status` повертає додаткове поле `refusalTag: {id, code, name}` або null. Збережений тег читається навіть після деактивації причини. При виході з відмови він очищується правилами T6712, попередній код залишається в історії. Пауза з відмови зберігає тег.

Представлення `object_refusal_tags` містить `object_id`, `reason_id`, `code`, `name`, `region_id`, `manager_id`, `status_id`, `version`. Воно придатне для фільтрації та групування в аналітиці й відразу відображає поточний стан, без окремої синхронізації. Наприклад, кількість об'єктів з тегами у дозволеному регіоні:

```sql
SELECT reason_id, code, name, count(*) AS object_count
FROM object_refusal_tags
WHERE region_id = :permitted_region_id
GROUP BY reason_id, code, name;
```

Представлення не є відкритим HTTP API. Сценарій аналітики має застосовувати права та регіональні фільтри перед читанням. Окремий дашборд або Power BI інтеграція не входять до T6713.

## Задачі та погодження

Дія з задачами береться з поля переходу. Активні ручні відмови налаштовані як CANCEL_ALL: NEW, IN_PROGRESS, PAUSED та WAITING_APPROVAL стають CANCELLED у всіх етапах і наборах об'єкта. DONE, CANCELLED та задачі інших об'єктів зберігаються. Історія задач, outbox і повідомлення виконавцям записуються в тій самій транзакції.

При налаштованому `is_refusal_entry` активні PENDING-запити статусу переходять у CANCELLED із користувачем, який поставив відмову. Записуються STATUS_REQUEST_CANCELLED в аудит, OBJECT_STATUS_APPROVAL_RESOLVED в outbox і повідомлення ініціатору OBJECT_STATUS_APPROVAL_CANCELLED. Повторне підтвердження такого запиту повертає 409. Інші зміни об'єкта, як і раніше, роблять очікуваний запит STALE.

Об'єкт блокується перед задачами та погодженням. Відмова й погодження, що виконуються одночасно з однією версією, дають один успішний запис і один 409. Помилка будь-якого запису відкочує статус, тег, задачі, погодження, історію, повідомлення та outbox.

Об'єкт не видаляється і продовжує брати участь у пошуку дублей, з ознакою `refused=true` для користувача з повним доступом. Чужі об'єкти зберігають обмежене відображення за правилами T5771.

## Міграція

Окремий changeset `20261006-object-refusal` додає класифікацію помилок і представлення тегів. Опубліковані міграції не змінені. Rollback видаляє тільки нове представлення та таблицю класифікації; об'єкти, причини, задачі та погодження зберігаються. Повторне застосування не змінює наявні дані.

Додатковий changeset `20261013_refusal_cancel_all` встановлює CANCEL_ALL для активних ручних переходів з `is_refusal_entry`. Системне рішення ІК, неактивні правила та повернення з паузи у попередню відмову не змінюються. Службова таблиця `object_refusal_task_policy_backup` зберігає попередню дію і версію застосованого правила для точного відкату. Rollback відновлює тільки правила, яких не змінювали після міграції, та видаляє службову таблицю. Об'єкти, задачі, історія й налаштування, змінені пізніше, не переписуються. Повторне застосування Liquibase не дублює записи й не збільшує версії правил.
