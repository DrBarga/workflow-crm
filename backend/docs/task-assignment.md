# Назначение исполнителей

T5810, FR-27. Источники: критерии задачи, ответы Влада о подтверждении перехода и уточнение Богдана от 28.10.2026 о региональных ролях.

## Подбор по шаблону

| Правило | Исполнитель |
|---|---|
| `OBJECT_MANAGER` или роль `MANAGER` | Активный владелец объекта. Другой менеджер в регионе не заменяет владельца. |
| Роль `CONTRACT_MANAGER` при согласовании перехода | Активный пользователь этой роли, который подтверждает переход в статус-триггер. Инициатор запроса и читатель карточки не считаются согласующими. |
| Роль `CONTRACT_MANAGER` без согласования | Общий подбор по роли. |
| `REGIONAL_ROLE` | Сначала активные пользователи роли в регионе объекта. Для сетевой роли при отсутствии местных кандидатов предлагается ручной выбор по сети. |
| `NETWORK_ROLE` | Активные пользователи роли по сети с обязательным ограничением региональных ролей. |
| `EXPLICIT_USER` | Указанный активный пользователь с доступом к региону объекта. При недоступности предлагаются активные кандидаты в допустимой области. |

`MANAGER` и `REGIONAL_MANAGER` допускаются только в закреплённых за ними регионах, независимо от правила шаблона. Поиск по сети не снимает это ограничение. Это согласованное уточнение заменяет прежнюю формулировку критерия о сетевом поиске для любой роли.

География проверяется через публичный API Users. Текущий справочник регионов плоский; учитываются все регионы пользователя. Устаревшая иерархия областей не восстанавливается.

Один подходящий кандидат назначается автоматически. Несколько кандидатов возвращаются целиком, по имени и UUID, для выбора в модалке. Сетевой запасной список для `REGIONAL_ROLE` требует явного выбора даже при единственном кандидате. Деактивированные пользователи исключаются.

Если владелец объекта недоступен, назначение роли «Менеджер» блокируется; сначала необходимо восстановить доступ или перепривязать объект. Автоматическая подмена владельца другим менеджером не выполняется.

## Превью и создание

В каждом элементе `assignment` содержит `issue`, `selectionRequired`, `candidates` и `message`. При отсутствии доступных пользователей список пуст, возвращается сообщение с ролью и предложением обратиться к Администратору. Элемент остаётся в превью.

Выбор передаётся картой `assignees`: UUID элемента шаблона → UUID пользователя. После выбора клиент повторяет `POST /api/objects/{id}/task-sets/preview` с этой картой. Токен выдаётся только для полностью назначенного набора. То же тело с токеном направляется в `/task-sets`. Выбор включён в токен, ключ повторного запроса и сохранённую команду очереди.

`PATCH /api/objects/{id}/ic-decision` принимает ту же карту `assignees`. Если требуется выбор, решение ІК возвращает `saved=false`, список кандидатов и пустой токен. После выбора повторный запрос выдаёт токен; подтверждение сохраняет решение и выбранных исполнителей одной транзакцией.

При переходе с согласованием инициатор отправляет обычный `POST /status` и получает `approvalRequestId` без подтверждения набора. Его POST-превью информационное, `confirmationToken=null`. Согласующий запрашивает `/task-sets/preview` с `approvalRequestId`, выбирает недостающих исполнителей и подтверждает набор один раз. Договорная роль подставляется по согласующему уже в этом превью.

Незаполненный выбор, неподходящая роль или регион, чужой элемент шаблона дают 422. Подмена автоматически назначенного исполнителя в превью запрещена. Изменившийся подтверждённый план даёт 409. Воркер повторно проверяет выбор и доступы; при ошибке статус и набор не сохраняются частично.

## Ручная смена после создания

`GET /api/objects/{id}/tasks/{taskId}/assignees` возвращает доступных кандидатов.

`PATCH /api/objects/{id}/tasks/{taskId}/assignee` принимает:

```json
{"assigneeId":"00000000-0000-0000-0000-000000000001","version":0}
```

Права следуют действующему правилу перепривязки объекта: Провідний в своих регионах и Директор по сети. Менеджер, CEO, Администратор и договорной отдел этот endpoint не используют. Это выбранное правило для неуточнённого критерия «ролям с правом»; оно не меняет права выбора в модалке перехода.

Проверяются объект задачи, активность исполнителя, роль и область назначения из исторической версии шаблона. Правка черновика не меняет права уже созданной задачи. Владелец остаётся обязательным для задач, привязанных к владельцу. Завершённые и отменённые задачи не переназначаются.

Смена увеличивает версию задачи и одной транзакцией записывает `task_assignment_history` и `TASK_REASSIGNED` в outbox. Статус, срок, зависимости и признак передачи от предыдущего владельца сохраняются. Повтор того же назначения с текущей версией не создаёт запись; устаревшая версия возвращает 409. Пользователи и объект блокируются в том же порядке, что при перепривязке объекта.

Frontend и доставка уведомлений относятся к отдельным задачам. Здесь реализованы backend-контракты назначения и событие изменения исполнителя.
