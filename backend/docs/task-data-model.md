# Модель задач и шаблонов

Миграция `20261012-task-model` расширяет существующие таблицы задач. Миграция `20261019-task-workflow-fields` добавляет поля постановщика, проверки результата и эскалации. Коды элементов используются совместно с T5770; `20261024-task-model-revisions` закрепляет их неизменность и добавляет признак ручной паузы. Публичные контракты Objects и прежние коды статусов сохраняются.

## Сущности

| Таблица | Назначение |
| --- | --- |
| `task_templates` | Редактируемая привязка шаблона к статусу-триггеру и типу договора |
| `task_template_items` | Прежние редактируемые элементы, используемые текущим сценарием Objects |
| `task_template_versions` | Сохранённые определения шаблона: номер редакции, отпечаток, статус-триггер, тип договора |
| `template_items` | Элементы конкретной редакции: постоянный код, название, правило срока, правило назначения, порядок, необходимость проверки, роль получателя результата, срок эскалации |
| `template_item_dependencies` | Предшественники элемента в пределах одной редакции |
| `task_sets` | Набор задач объекта, созданный по конкретной редакции при входе в статус-триггер |
| `tasks` | Название, объект, исполнитель, постановщик, получатель результата, необходимость проверки, срок, статус, ручная пауза, время создания и завершения, источник, набор, версия записи |
| `task_dependencies` | Предшественники задачи в пределах одного объекта |
| `task_statuses` | Справочник шести статусов задач |
| `contract_types` | Существующий общий справочник типов договора |

Связи между модулями хранят UUID. Таблицы зависимостей запрещают повторные связи и зависимость от себя. Составные внешние ключи запрещают смешивать редакции шаблона и объекты. Доменная модель редакции дополнительно проверяет неизвестных предшественников и циклы.

## Версии и наборы

`task_template_versions.revision` — номер сохранённого определения. `version` в задачах, наборах и редактируемых сущностях — версия записи для оптимистической блокировки. Это разные значения.

При подтверждении перехода Objects сохраняет определение шаблона и создаёт набор с задачами в той же транзакции. Одинаковое определение повторно использует сохранённую редакцию. Изменение названия, исполнителя, срока, порядка элементов, необходимости проверки, роли получателя или эскалации создаёт другую редакцию. Отпечаток вычисляется по значениям полей, поэтому изменение определения не зависит от ручного увеличения версии записи. Конкурентное сохранение сериализуется блокировкой по шаблону. Подтверждение перехода также учитывает настройки проверки: изменение после preview требует нового подтверждения.

Каждая созданная задача ссылается на `template_items` и `task_template_versions`. Старый `template_item_id` сохраняется для совместимости; удаление редактируемого элемента не удаляет сохранённый источник задачи. Адаптер не обновляет сохранённые редакции. Редактор шаблонов должен создавать новые определения через доменную модель, а не менять прежние редакции.

Набор хранит объект, редакцию шаблона, статус-триггер и время создания. ACTIVE-набор целевого статуса повторно используется при переходе без превью и новой нарезки; COMPLETED и CANCELLED позволяют создать новый набор. Состояния: `ACTIVE` — «Активний», `COMPLETED` — «Завершений», `CANCELLED` — «Скасований». Текущий сценарий возврата отменяет набор после отмены всех его незавершённых задач. Завершение задач и переход набора в `COMPLETED` относятся к следующему сценарию workflow Tasks.

Ручные задачи могут не иметь источника шаблона. При наличии источника обязательны редакция и набор. `completed_at` допускается только для `DONE`.

`tasks.author_type` различает `USER` и `SYSTEM`. Для автоматической генерации постановщик — система; `author_id` сохраняет пользователя, подтвердившего переход, для трассировки. У ручной задачи `author_id` указывает постановщика. `result_recipient_id` ссылается на пользователя независимо от исполнителя; пока получатель не назначен, значение пустое. Источник и набор новой ручной задачи также пустые.

`tasks.manually_paused` хранит признак «на паузі вручну» отдельно от статуса. Значение по умолчанию — false; true допустимо только при PAUSED. Историческим задачам, включая PAUSED, миграция оставляет false: причина прежней паузы неизвестна. Отмена снимает признак в одной транзакции со статусом, историей и уведомлениями. Поле включено в доменную модель; ручная пауза, возобновление и взаимодействие с паузой объекта реализуются отдельным workflow T6725.

## Правила элементов

`code` — постоянный код элемента для условий перехода объекта. Он задаётся при создании; при отсутствии значения формируется `ITEM_` с UUID исходного элемента. Код уникален в редактируемом шаблоне и в сохранённой редакции. Переименование, изменение срока, исполнителя и выпуск новой редакции сохраняют код. Менять код, исходный элемент или принадлежность сохранённой редакции нельзя; для другого элемента создаётся новая запись.

Триггеры БД проверяют код новой редакции по редактируемому элементу и прежним редакциям. После удаления редактируемого элемента сохранённые источники задач продолжают защищать его код. Параллельное создание редакций сериализует проверку по UUID исходного элемента. Индекс `template_items(source_item_id)` поддерживает эту проверку. Если в существующих данных одному исходному элементу уже соответствуют разные коды или шаблоны, миграция останавливается без изменений и требует согласовать исправление данных; исторические коды автоматически не переписываются.

Правило срока хранит основу расчёта и смещение 0–3650 дней. По критериям T5809 сроки рассчитываются в календарных днях от перехода объекта (`FROM_START_CALENDAR`). Ранее предусмотренное значение `FROM_START_BUSINESS` сохранено для совместимости схемы, текущая генерация его не использует. Правило назначения: конкретный пользователь (`EXPLICIT_USER`), менеджер объекта (`OBJECT_MANAGER`), роль региона (`REGIONAL_ROLE`) или сети (`NETWORK_ROLE`). Для конкретного пользователя нужен `assignee_id`, для роли — `role_id`; несовместимые параметры запрещены.

Существующая генерация Objects сохраняет правила `FROM_START_CALENDAR` и `EXPLICIT_USER`. Разрешение ролей, назначение получателя результата и запуск зависимых задач выполняются в отдельных сценариях Tasks; эта миграция задаёт модель их хранения.

Редактируемый элемент и его сохранённая редакция содержат `needs_review`, `result_recipient_role_id` и `escalation_days`. Эскалация допускает 0–3650 дней; пустое значение означает отсутствие настройки. Ссылки на роли и пользователей защищены внешними ключами. Для прежних записей `needs_review=true` сохраняет описанный ранее сценарий с обязательной приёмкой; миграция не выбирает получателя и не назначает срок эскалации. Это совместимость прежних данных, а не утверждённая настройка четырёх задач «Підготовка на ІК». Их значения должны быть согласованы отдельно и внесены в сид шаблона в T5805.

## Справочники

| Код статуса | Название |
| --- | --- |
| `NEW` | Не розпочата |
| `IN_PROGRESS` | У роботі |
| `PAUSED` | На паузі |
| `WAITING_APPROVAL` | На погодженні |
| `DONE` | Завершена |
| `CANCELLED` | Скасована |

Миграция не меняет существующий справочник `contract_types` из T5770: `PRIMARY` («Основний») и `PRELIMINARY` («Попередній»). Шаблоны и их редакции ссылаются на этот справочник; отдельный дублирующий сид не создаётся.

## Перенос и откат

Существующие задачи получают наборы по объекту, статусу и шаблону. Выполненным задачам проставляется дата завершения из `updated_at`. Сохранённая редакция фиксирует доступное на момент миграции определение; прежние изменения шаблонов, которых нет в базе, восстановить нельзя. Название, срок, исполнитель, статус и версия существующей задачи не меняются.

Откат выполняется в обратном порядке: сначала `20261019-task-workflow-fields`, затем `20261012-task-model`. Он удаляет добавленные связи, поля и таблицы и возвращает прежнее название статуса `DONE`. Существующие задачи, определения и справочник типов договора сохраняются. Повторный запуск Liquibase не создаёт повторный сид.

Перед откатом предыдущих изменений сначала откатывается `20261024-task-model-revisions`. Он удаляет признак ручной паузы, новые триггеры и индекс, возвращает прежние значения по умолчанию для кодов, сохраняя сами коды. Если остались задачи с ручной паузой, откат запрещён, чтобы не потерять причину паузы. Сначала требуется завершить соответствующее действие либо согласовать перенос этого состояния.

Проверки: сохранение данных и точной схемы после отката, повторное применение, отсутствие изменений от preview, атомарное создание, повторное подтверждение, сохранность прежнего источника, конкурентное сохранение редакции и откат прерванной транзакции.
