# Расчёт сроков задач

Срок задачи равен дате перехода объекта в статус-триггер плюс `deadline_offset_days` элемента шаблона. Расчёт выполняет `DeadlineRule.calculate`. Правило `deadline_rule=FROM_START_CALENDAR` хранится в `task_template_items`; смещение задаётся в пределах 0–3650 дней. Изменение срока в шаблоне не требует изменения Java-кода.

Считаются календарные дни, включая выходные и праздники. При нулевом смещении срок совпадает с датой перехода. Например, переход 23 октября с правилом +2 дня даёт срок 25 октября. Предшественники влияют на возможность старта, но не участвуют в расчёте срока: задача с правилом +0 и предшественником +5 сохраняет срок в день перехода.

Превью и подтверждённый переход используют один источник даты `ObjectTaskTriggerDate` на основе `Clock` в часовом поясе Europe/Kyiv. Превью показывает результат возможного перехода сегодня. При изменении даты до подтверждения план пересчитывается; прежнее подтверждение отклоняется с 409, если сроки изменились. Ожидание согласования не фиксирует дату первоначального запроса: расчёт относится к фактическому переходу после согласования.

Созданные задачи сохраняют рассчитанные даты, а неизменяемая версия шаблона — календарное правило и смещение. Правки исходного шаблона не меняют существующие сроки. Одинаковое правило при разных датах перехода даёт одну версию шаблона, а не новую версию на каждый день.

Миграция `20261022_task_deadlines` добавляет правило в редактируемые элементы. Для существующих строк сохраняется прежнее календарное поведение. Ограничение БД разрешает только `FROM_START_CALENDAR`; расчёт рабочих дней не входит в текущие требования. Откат удаляет новый столбец, сохраняя смещения и данные задач; повторное применение не дублирует данные. Исторические версии шаблонов не изменяются.

Основание: T5809, FR-26 и NFR-27 в Product Requirements Documents KeySpace. API сохраняет прежний формат: даты передаются в ISO `YYYY-MM-DD`.
