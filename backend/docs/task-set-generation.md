# Создание набора задач

T5808. Требования: FR-07, FR-25–29, FR-37–39, NFR-03/14/15; уточнения Влада от 21.10.2026.

## Подтверждение и HTTP

1. `POST /api/objects/{id}/task-sets/preview` принимает тело перехода статуса: `status`, `version` и необходимые для перехода поля (`contractSignedDate`, `contractTypeId`, `openingDate`, `refusalReasonId`). Возвращает `ObjectStatusResult` с `saved=false`, списком задач и `confirmationToken`. Объект, задачи и очередь не изменяются.
2. `POST /api/objects/{id}/task-sets` получает то же тело с выданным `confirmationToken` и обязательным заголовком `Idempotency-Key`. Для нового задания возвращает `202`, `Location` и `state=QUEUED`. HTTP-запрос сохраняет задание, не ожидая RabbitMQ и создания задач.
3. `GET /api/objects/{id}/task-sets/jobs/{jobId}` возвращает состояние задания и `taskSetId` после успешного создания. Ответы имеют `Cache-Control: no-store`.

Ключ содержит 1–128 символов: латинские буквы, цифры, `.`, `_`, `:`, `-`. Отсутствующий заголовок даёт 400; неверный ключ или отсутствие подтверждения — 422. Повтор ключа с тем же телом возвращает прежнее задание: 202, пока оно в очереди, затем 200 с результатом. Другое тело с использованным ключом даёт 409. Повтор того же подтверждения с новым ключом возвращает прежнее задание, если оно ожидает обработки, согласования или уже выполнено. После окончательной ошибки новый ключ позволяет повторить попытку; план и права проверяются заново. Сохранённые ключи ограничены пользователем; чужой результат не выдаётся.

`GET /task-preview?status=...` из T5807 остаётся расчётным просмотром: он сохраняет элементы с неопределённым исполнителем. POST-превью дополнительно проверяет права перехода и обязательные поля. Неопределённые исполнители остаются в списке с кандидатами; до полного выбора confirmationToken пуст. Выбор передаётся картой assignees (UUID элемента → UUID пользователя). Подтверждение из прежнего `POST /status` также подходит для нового endpoint.

Маршруты смены статуса, дат и решения ІК сохраняются. Для перехода с согласованием инициатор больше не подтверждает набор: POST /status создаёт запрос согласования, а его превью остаётся информационным. Асинхронное подтверждение выполняется через новый `/task-sets`; клиент должен использовать его для этого сценария. Изменения интерфейса в T5808 не входят.

## Очередь и транзакция

`object_task_set_jobs` хранит команду и подтверждение, `object_task_set_keys` — ключи повторных запросов. Ожидающее задание для объекта одно. Публикация в долговечную очередь `workflow.task-set-generation` выполняется отдельным воркером с persistent-сообщением, publisher confirm и проверкой возврата сообщения. В RabbitMQ передаётся только UUID задания.

При недоступном брокере задание остаётся в PostgreSQL, объект не меняется. Неподтверждённая доставка повторяется; отправленное, но не обработанное задание публикуется повторно через 30 секунд. Это покрывает потерю соединения и перезапуск процесса. Получатель блокирует строку задания; обработанное задание повторно не выполняется. Несколько экземпляров приложения могут безопасно получить одну доставку.

Воркер заново проверяет права, версию объекта, правило перехода, шаблон, сроки, исполнителей, получателей и зависимости. Подтверждение связано с полным планом. Изменение данных, включая переход на другую календарную дату, завершает задание ошибкой `PREVIEW_CHANGED`; пользователь перечитывает превью. Другой состав без подтверждения не создаётся.

Смена статуса объекта, отмена задач по политике перехода, снимок шаблона, набор, все задачи, зависимости, уведомления, аудит, история и успешный результат задания фиксируются одной транзакцией. Ошибка откатывает всё. Состояние ошибки записывается отдельной транзакцией. Транзитные ошибки БД повторяются с задержкой пять секунд, максимум три попытки. Остальные ошибки завершают задание с `FAILED`. Повтор старого ключа возвращает тот же результат ошибки.

Если правило требует другую роль, инициатор получает approvalRequestId через POST /status без подтверждения набора. Объект и задачи до решения не меняются. Уже сохранённые задания прежнего протокола могут завершиться AWAITING_APPROVAL; их обработка сохраняется. Согласующий передаёт `{ "approvalRequestId": "..." }` в `/task-sets/preview`, затем тот же UUID и полученный `confirmationToken` в `/task-sets` с собственным ключом. Решение, статус и набор применяются в очереди; HTTP согласующего также не ждёт создания задач. После обработки оба задания получают результат. Прежний API согласования остаётся совместимым; его окончательное решение также обновляет результат задания.

## Состав и история

Задачи получают автора `SYSTEM`, исполнителей и получателей из подтверждённого плана. Задачи без предшественников начинают с `IN_PROGRESS`, с предшественниками — с `PAUSED`; сроки считаются от даты триггера в календарных днях. Для стартовых задач в той же транзакции записываются уведомления `TASK_STARTED`. Доставка email и Telegram относится к Notifications & Escalations.

`TASK_SET_CREATED` содержит UUID набора, шаблона и количество задач в истории объекта и журнале. Исторические версии шаблона и уже созданные задачи не меняются при правке черновика.

Уникальный индекс `ux_task_sets_active_trigger` запрещает два активных набора для пары «объект + статус-триггер». Возврат к существующему активному набору использует его. Отменённый набор не мешает создать новый. Ключ и токен не обходят правила доступа или перехода.

## Настройки и проверки

`TASK_SET_WORKER_ENABLED` включает публикацию и потребителя; по умолчанию true. `TASK_SET_POLL_DELAY_MS` задаёт интервал публикации, по умолчанию 500 мс. Для тестов доступны `app.tasks.generation.consumer-enabled` и `app.tasks.generation.initial-delay-ms`. RabbitMQ использует общие `RABBITMQ_*` настройки приложения.

`ObjectTaskSetQueueIT` проверяет подтверждение 100 задач за время менее трёх секунд, повторы, конкуренцию, подмену тела, точный состав, зависимости, права, согласование и полный откат при ошибке на втором элементе. `ObjectTaskSetRabbitIT` использует настоящий RabbitMQ: подтверждённая доставка, дубли сообщений, остановка и восстановление брокера. `TaskSetQueueMigrationIT` проверяет повторный changelog и откат схемы. Замер HTTP на тестовом стенде не заменяет измерение на инфраструктуре заказчика.
